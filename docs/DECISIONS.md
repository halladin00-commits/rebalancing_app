## 정해진 것 (더 묻지 않는다)

### 2026-08-30 · 허용 편차 잠금의 예산 초과도 고쳤다

기본값을 바꾸고 확인하다 찾았다. 종목을 빼지 않아도 같은 문제가 났다 —
허용 편차 안에 든 종목이 잠기면 그 돈이 두 번 세어졌다.
사용자가 `고치자`로 승인했다.

**고치다 알게 된 것:** 나눠주기를 그냥 넓히면 안 됐다. 잠긴 종목이 목표보다
**적게** 갖고 있을 때는 남는 돈을 현금으로 두는 게 맞고, 기존 코드가 그걸
의도적으로 그렇게 해뒀다(`rebalancer_threshold_test.dart`가 지키고 있었다).
억지로 나눠주면 다른 종목이 목표를 넘어간다.

그래서 목표 금액을 **두 상한 중 작은 쪽**으로 잡았다.
- 제 목표 비중 — 넘으면 목표를 지나쳐 산다
- 남은 예산의 제 몫 — 넘으면 없는 돈으로 산다

잠긴 종목이 목표보다 많으면 예산 쪽이, 적으면 목표 쪽이 작아진다.

### 2026-08-30 · 결정 4건 — 전부 내 제안대로

사용자가 `전부 네 제안에 동의해`라고 답했다.

| 안건 | 결정 |
| --- | --- |
| 리밸런싱 기본 계산 | **`나머지 종목에`로 바꿈** (적용 완료) |
| 배당 기록 | 사용자가 숫자를 직접 볼 수 있을 때 |
| 예수금 차감 토글 | 안 만든다 |
| 업로드 통째로 되돌리기 | 나중에 |

`Rebalancer.calculate`의 `redistributeExcluded` 기본값을 `true`로 바꿨고,
조정 제안 화면도 `나머지 종목에`가 기본 선택이다. `예수금에 남김`은 골라야
나오는 동작으로 남겨 뒀다. 옛 동작이 낼 수 없는 계획을 낸다는 것을
`그 대신 낼 수 없는 계획이 나온다 — 이래서 기본값에서 뺐다` 테스트가 지킨다.

### 2026-08-29 · `StockTransaction` 확장 — **하지 않는다**

시안 3개(v22b 손익 구성 표, v16d 예수금, v17a 수수료·환율 시트)를 **비워 둔다.**
사용자와 논의해 결정했다.

- **수수료·세금·환율은 안 한다.** 수수료는 거래액의 0.0x%라 수익률을 눈에 띄게
  바꾸지 않는데, 거래마다 입력 칸이 늘어 기록 자체를 안 하게 된다. 거래별 환율은
  `_priceInBase`를 타는 모든 과거 계산에 파급돼 위험 대비 실익이 적다.
- **배당은 실제 구멍이 맞다.** 결산에서 현금은 시작값·끝값에 똑같은 오늘 잔액이
  들어가(`settlement_service.dart:296`) 기간 중 현금 변동이 수익률에 정확히 0
  기여한다. 배당을 받아 현금에 더해도 안 잡힌다. 다만 **사용자가 돌아와 숫자를
  직접 볼 수 있을 때** 한다 — 돈 계산의 오류는 앱이 안 죽고 테스트도 통과하는
  채로 숫자만 틀리므로, 무인 작업에 맞지 않는다.

### 2026-08-30 · 합산 결산 수익률의 정의 — **결정됨 · 적용 완료** (`a9fc6d1`)

한 화면에서 수익률 정의가 두 가지로 갈린다. 실기기에서 발견했다.

| 자리 | 계산식 | 코드 |
| --- | --- | --- |
| 전체 결산 **헤더** | `손익 ÷ 기초자산` (단순) | `settlement_service.dart:688` |
| 전체 결산 **포트별 행** | `손익 ÷ (기초자산 + 가중현금흐름)` (Modified Dietz) | `settlement_service.dart:422` |
| 포트 **개별** 결산 헤더 | Modified Dietz | 같은 값을 그대로 씀 |

셋 중 헤더만 혼자 다르다. 기간 중 매매가 없으면 가중현금흐름이 0이라 두 식이
같아지므로 여태 안 드러났다. **매매한 달에만 어긋난다** — 하필 리밸런싱한 달이다.

실측(2026-08-30, 사장님 데이터): 8월은 전 종목을 8/23에 샀다.

- 헤더: 기초자산 0 → `rateAvailable = false` → **`—`**
- 바로 밑 위탁계좌 행: 분모 ₩58.2M → **`+2019.74%`**
- 같은 화면에서 "수익률을 낼 수 없다"와 "+2019.74%"가 동시에 있다

금액(₩)은 두 방식이 같다. **어긋나는 건 % 하나다.**

**제안**: 헤더도 Modified Dietz로 통일한다. 나머지 두 자리가 이미 그것이고,
기간 중 입금을 수익으로 치지 않으려고 존재하는 식이다.

**왜 혼자 안 정하나**: 손익 계산 정의 변경이고, 사장님이 투자일기에 그대로
옮겨 적는 숫자다. 바꾸면 과거에 적었던 %와 달라진다.

**결정**: 사장님이 제안대로 승인. `periodReturn()`을 두고 세 자리가 모두
지나게 했다. 딸린 질문(기초자산 0인 기간)은 위임받아 아래로 정했다.

| 상황 | 식 |
| --- | --- |
| 기초자산 > 0 | Modified Dietz — `손익 ÷ (기초자산 + 가중현금흐름)` |
| 기초자산 = 0, 기간 중 입금 | **넣은 돈 대비** — `손익 ÷ 순입금` |
| 그 외 | 못 낸다 (`—`) |

두 번째 줄이 (가)(나)(다) 중 어느 것도 아닌 네 번째 답인 이유: 기초가 0인데
Dietz를 쓰면 분모가 기간의 일부만 남아 `+2019.74%`가 나오고(가는 못 쓴다),
`—`로 비우면 첫 달 수익률을 영영 못 보며(나도 아쉽다), 보유 기간을 밝히는
것만으로는 숫자 자체가 여전히 부풀려져 있다(다는 부족하다).
**처음부터 들고 있지 않았다면 "기초 대비"라는 말이 성립하지 않는다** —
사람이 아는 값은 넣은 돈 대비 얼마다.

실측으로 검증됐다. 8월(전 종목 8/23 매수):

| | 고치기 전 | 고친 뒤 | 자산 탭 |
| --- | --- | --- | --- |
| 전체 | `—` | **+218.83%** | +218.69% |
| 위탁계좌 | +2019.74% | **+418.38%** | +417.88% |
| ISA계좌 | +404.50% | **+83.68%** | +83.69% |

검산: (281M×418.38 + 415M×83.68) ÷ 696M = 218.8%. 헤더가 자기 행들과
맞고, 결산 탭과 자산 탭이 같은 말을 한다.

캐시는 `settlement_cache_v3`으로 올리고 v2를 지운다 — 옛 식으로 낸 값이
남으면 다시 계산하지 않아 틀린 수익률이 그대로 굳는다.

### 2026-08-30 · 종목 추가 폼의 목표 비중 합 — **막지 않고 알린다**

`목표 비중 설정` 화면은 합계가 100%가 아니면 저장을 막는다. 종목 추가 폼은
안 막아서, 60%짜리 하나만 넣어 두고 조정 제안 화면에서 막다른 길에 부딪히는
일이 있었다. 사용자가 "알아서 해봐"로 위임해 아래로 정했다.

**막지 않는다.** 종목을 하나씩 넣는 동안 합계가 100이 아닌 건 정상이다.
막으면 **첫 종목부터 못 넣는다** — 어떤 비중을 넣어도 혼자서는 100이 안 된다.
합계를 강제할 자리는 전체를 한 화면에서 정하는 `목표 비중 설정`이 맞다.

**대신 넣는 자리에서 알린다.** 목표 비중 칸 옆에 실시간으로 적는다.

| 상태 | 문구 | 색 |
| --- | --- | --- |
| 합계 100% | `합계 100%` | 브랜드(초록) |
| 모자람 | `합계 60% · 40% 남음` | 경고(주황) |
| 넘침 | `합계 115% · 15% 초과` | 경고(주황) |

경고가 아니라 **안내**다. 저장 버튼은 늘 활성이다. 안 보여주면 조정 제안
화면에서 막힌 뒤에야 알게 되는데, 그때는 원인이 어디였는지 알기 어렵다.

`ItemFormScreen`에 `otherWeights`(이 종목을 뺀 나머지 합)를 넘긴다.
편집일 때는 자기 자신을 뺀다 — 안 그러면 자기 비중이 두 번 세어진다.
